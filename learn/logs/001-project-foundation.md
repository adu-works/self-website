# 日志 001：需求与 AI 协作流程初始化

> 日期：2026-09-16 ｜ 对应路线图：G1 需求阶段 ｜ 涉及代码：无业务代码；涉及 README.md、AGENTS.md、docs/

## 这次做了什么

读取 system-agent-ai 的个人网站设想，在空的 self-website 目录建立 PRD、阶段状态、评审入口、协作 SOP 与交互约定记录。所有产品内容仍是草案，没有制作原型或开始功能实现。

## 实现顺序（先写什么、再写什么，为什么）

1. **先读需求来源和目录现状**，确认已有材料与空仓库，避免重复建设或误把愿景当完成状态。
2. **然后区分需求、假设和待确认项**，先定义用户要评审什么，再定义文档目录。
3. **再写 PRD 与评审清单**，将长期方向拆成可讨论的产品增量，补足验收和边界。
4. **最后固化阶段确认、交互记录和学习日志**，让下一轮能准确接续，不越过用户关口。

这里遵循本项目 G1 → G2 → G3 → G4；video-digest 的产品路线图不适用于本独立网站，只借用其教学日志模板。

## 关键决策

| 决策点 | 选择 | 为什么 | 落选方案 & 为什么 |
|---|---|---|---|
| 首次交付 | 文档与 PRD | 用户要求先评审需求 | 直接脚手架开发：跨过原型与方案确认 |
| 首版范围 | 提议先展示，后 Agent | 真实内容是问答的前提，控制范围 | 一次全部做完：风险大，且用户尚未批准 |
| 原型工具 | 暂不定 | 需要先确定评审目标 | 直接指定 Figma：用户只是询问，并未选择 |
| 技术栈 | 记录为候选 | 保留源材料，不提前定实施方案 | 把技术建议当定案：会影响后续评审 |
| SOP | 独立活文档并记录真实指示 | 避免规则只存在聊天里 | 完工后一次总结：容易丢失原因和纠正历史 |

## 语言课堂（本次用到的 TS/Python 知识点）

本次没有产品 TS/Python 代码；不虚构语法课堂。文档批量落盘借用了 Python 的 `Path` 与字典，但这不是网站的实现或技术选型。

Markdown 是普通文本的排版约定：`#` 表示一级标题，`##` 表示二级标题；`[名字（历史）](https://github.com/adu-works/self-website/blob/fc7eb6b/learn/logs/路径)` 是链接，路径相对于当前文档的位置；`- [ ]` 是未完成项，不能未经确认改成完成项。修改需求时，同时更新文档版本和评审对象，能避免批准了旧稿却执行新稿。
