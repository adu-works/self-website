## 已观察到的经验

- 2026-09-16：源材料混合了愿景、技术建议和季度计划；本次先分离为需求提案、待确认项和后续阶段，避免把历史计划当作当前授权。后续效果尚待验证。
- 2026-09-16：用户直接跳过 PRD 评审要求原型。处理方式是**先问清关口如何处理再动手**，而不是自行判断"用户既然要就等于确认了"。四个选项（关口、范围、内容来源、形式）一次问完，用户一次作答即可开工，比逐个追问省事。这条做法值得进入 SOP。
- 2026-09-16：真实内容未确认时，原型用"结构真实 + 内容标注为示例"的方式推进，既没有阻塞，也没有虚构用户经历。代价是原型评审只能评结构，内容问题仍要单独回答。
- 2026-09-16（用户指出）：第一版视觉是直接按默认审美写的，没有用任何设计方法。用户要求改用设计类 skill 后重做，当时 Agent 认为围绕“证据可核对”的方向更合适；这是历史自评，不是用户审美确认。教训：**有现成方法论时先读再做**，"能看"不等于"有设计"。
- 2026-09-16（3D 入口）：用户没有接受「完全不做游戏」，而是给出结构——3D 放首页，进来才是桌子。这说明反对的是「用开车替换产品」，不是反对可玩性。以后类似分歧先问**放在哪一层**，再问做不做。

- 2026-09-16（第二次视觉返工）：用户仍不满意，要求"高级"并做动效。这次先**调研同类站点**（rauno.me、paco.me、Codrops 2026 专题）再定方向，结论是工程师个人站的高级感来自克制与精度，不是元素密度；动效的关键是错峰编排。当时 Agent 写“按这个重做后才达标”，本轮撤回该结论：没有用户验收证据，且用户仍反馈原型丑。教训：审美问题不能靠自己"再试一版"，要先找参照系。另外发现一个有效做法——给原型加「评审标注」开关，把需求编号等元信息一键收起，用户才看得清设计本身。
- 2026-09-16（返工）：用正则批量把中文直引号换成弯引号时，没有排除标签属性和内联脚本，导致 `aria-label="管理端分区"` 之类的属性结束引号被改坏、管理端导航渲染异常。修复方式是按区域处理（标签与脚本内一律还原直引号，只在正文文本里成对转换），并加一条校验：每个标签内引号必须成对。教训见 SOP。

触发：用户指出审美不满意、许多决定没有确认。影响：首版范围与视觉方向需重新评审。处理：更新 PRD v0.2、逐站核对参考、提供三方向、保留旧稿，区分本轮直接证据与历史 AI 陈述。预防：设计选择需明确来源和范围；不得把“能运行”“用了 skill”写成“审美达标”。
