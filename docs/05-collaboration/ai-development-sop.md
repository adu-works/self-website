# AI 辅助开发 SOP

> v0.5 · 2026-09-16 · 过程草案，随真实协作更新。
> 阶段确认顺序是用户明确要求；工程细节目前是工作约定与待实践方法，不能声称已验证成功。

## 1. 启动：先读上下文，再提出方案

用户提供目标与材料。AI 读取项目约定、现状和来源，区分已有事实、用户决定、AI 建议及未知项，先在已授权范围内产出可评审成果。不要把过去文档中的设想直接当今天的批准。

每次恢复工作先读状态、PRD 与交互约定；避免换任务或换 Agent 后丢失确认边界。

## 2. 固定顺序与交付

| 阶段 | AI 先做什么 | 用户确认什么 | 确认前禁止做什么 |
|---|---|---|---|
| 需求 | 读来源、搭文档目录、写 PRD、标注假设与验收条件 | 需求版本、首版范围及保留问题 | 制作原型、提前编写实现方案、开发功能 |
| 原型 | 按批准需求准备演示，检查关键路径和异常状态 | 页面、交互、内容层级与演示版本 | 编写正式实现方案与规划、接真实业务写操作 |
| 方案规划 | 解释技术取舍，定义模块、验证与交付步骤 | 方案、规划、风险与实施范围 | 开始功能实现 |
| 实现 | 先测试纯逻辑，小步实现，验证并写教学日志 | 阶段验收及需确认的实际发布/写入 | 擅自扩张范围、把未验证能力说成完成 |

## 3. 怎样确认，怎样改需求

确认必须绑定具体交付物版本与范围，有用户原话或可追溯对话摘要。只说“这个不错”可能是局部认可，不能自动升级为阶段批准。用户明确批准过的工作不重复索要许可。

新需求先记入交互约定，说明影响需求、原型、方案中的哪一项。AI 可在当前阶段内直接修订；影响已经批准的范围时展示差异，请用户确认受影响内容，保留其他已确认决定。未回答的问题继续标注未知，等待不是同意。

区分两类确认：开发阶段确认控制是否进入下一阶段；产品内写操作确认控制站长 Agent 是否执行某次变更。前者不能代替后者。

### 用户要求跳过关口时怎么办（2026-09-16 实际发生）

关口保护的是用户，放行权也在用户。用户直接要求下一阶段交付物时，AI 既不能自行认定"用户既然要就等于确认了"，也不该用流程把人挡回去，而是**在动手前一次问清所有会影响返工的选择**，得到答复即开工，并把授权原话与范围写进 `status.md`。

本项目实际用的四个问题，可作为跨阶段请求的通用模板：

1. 关口怎么处理：视为授权跳过、先补确认、还是边做边把偏差回写上一阶段文档？
2. 范围多大：只做已确认部分，还是包含尚未确认的后续能力？
3. 内容从哪来：用户现在提供真实材料，还是用**标注过的示例**占位？
4. 交付什么形式：不同形式能演示的东西不同（例如静态原型能演示状态机，静态视觉稿不能）。

要点：跳过关口的授权只覆盖"开工"，不自动等于上一阶段内容已确认；上一阶段文档仍要单独定版。

## 4. 每轮结束的记录动作

1. 更新实际交付物与版本，不只在聊天中答应修改。
2. 更新 `interaction-ledger.md`：新偏好、纠正、禁区及其来源；未有新规则则无需制造一条。
3. 更新 `status.md`：完成、未完成、待确认；有批准证据才改变阶段状态。
4. 新增学习日志：先做什么、为什么、关键取舍、实际知识点、检查方式和练习。
5. 遇到重要取舍时写决策记录；发生返工时记录原因、纠正措施及适用范围。
6. 给用户简洁交付说明：文件、验证结果、限制和最重要的下一步评审事项。

## 5. 实现阶段的方法原则

- 需求有编号，设计和验收能对应需求；不靠“看着完成了”判断成功。
- 确定性代码负责顺序、校验与权限；Agent 负责确实需要判断的局部任务。
- 外部工具输入输出明确、职责单一；程序测试检查执行正确，评估样本检查回答质量。
- 失败必须可见；区分模型回答失败、工具失败、网络失败与执行成功但结果不符合目标。
- 注释解释为什么；学习日志解释本次语法与修改路径，不把所有学习成本推给用户。
- 测试和验证按改动风险选择，记录真实执行结果，不追求没有意义的数量。
- 批量文本替换（正则 / 脚本改多文件）前先界定作用域：代码文件里"看起来一样的字符"在标签属性、字符串字面量和正文中含义不同。改完必须跑结构校验（标签引号成对、脚本语法通过、页面能正常渲染），不能只看 diff 行数。
- 有现成方法论（skill、规范、检查清单）时先读再做。界面工作尤其如此：先定设计方向再写 CSS，写完按可访问性清单逐项核对。
- 涉及审美的交付，**先向用户要 3–5 个他喜欢的参照链接**，再去调研；自己挑的参照系可能整体跑偏，而用户给的链接能一次定调。调研的作用是解释"为什么这样做"和提炼可执行手法，不是替用户选方向。方向要能用一句话说清它为什么属于这个产品，而不是"看起来不错"。
- 交互模型级别的改动（不只是调样式）动手前先用一次选择题确认方向与范围，猜错的返工成本远高于一次提问。
- 换外壳时优先保住已验证的内容：把既有页面装进新外壳（如 iframe + 嵌入模式），比把内容重新搬一遍更不容易破坏已通过验证的行为。
- 原型里的元信息（需求编号、演示说明、状态切换器）会干扰审美判断。给它们做一个统一开关，让用户能只看产品本身。
- 把验证委托出去（子 Agent、脚本、他人）时，结论要抽查：至少自己复现被标为"失败"或"可能未实现"的那几项，并确认产物（截图、日志、报告文件）真的存在。2026-09-16 的原型验证中，委托方报告的截图路径并不存在，且把一处"位置不当但已实现"的提示判成未实现。

## 6. 复盘与最终沉淀

每次阶段评审后，回答：哪些指示反复说了？哪些返工源于信息不足？哪些确认太早或太晚？哪些检查实际发现问题？据此更新 SOP，并区分个人偏好和跨项目通用方法。

项目结束时形成：通用流程、阶段交付模板、真实成功案例、失败及修复案例、Agent 可直接读取的约定、用户评审清单。去掉个人隐私、临时路径和未经验证的经验。当前只是首版框架，不能把目录建成视为 SOP 已最终沉淀。

## 7. 接手返工时的校正（v0.3 / 2026-09-16）

- 先核对 README、阶段表、交付正文与实际目录；版本名不一致时明确哪份是当前稿、哪份是历史，不虚构缺失快照。
- 分别记录用户原话、旧记录转述、Agent 提案、实测结果。仅提供参考链接不意味着选定一个风格；仅授权工具不意味着批准上线或生产架构。
- 参考调研应注明观察方式和加载限制，不能根据标题或空白截图推断完整交互。网站不是都具有同一个共同点。
- 审美通过由用户评审决定。不要把设计技能使用、代码检查、AI 自评当作用户满意证据。
- 当用户明确首版 Agent 能力时，允许按依赖分步实现，但产品首版完成线必须包含这些能力。
- 原型显示模拟结果，工程验收检查真实系统；两者不能互相替代。
- 新原型单独版本目录；示例/模拟标记不能随评审编号一起隐藏。

## 8. 参考站先走内容链（v0.4 / 2026-09-16）

用户指出需要多点击体验后，本次发现 Merodev 的场景其实承担完整导航，Gregory 的书本与项目板也能打开阅读面板。仅看加载页和首屏会漏掉决定性信息。

- 最少操作“进入 → 找到内容 → 打开 → 关闭/返回”，按网站类型增加拖拽、搜索、章节定位或参数调节。
- 分开记录动作、观察结果、设计推论；点击过不等于走通，看到按钮不等于功能已验证。
- 页面初次超时或输入无结果时，结合截图和新状态判断；必要时改用实际键入，不急于认定网站故障。
- 说明测试环境与限制。未完成的驾驶、长页滚动、手机体验不能写成通过；截图未保存就不能声称交付了截图证据。
- 新发现回写提案，明确替代旧的有限观察。研究深化不自动批准方向或解锁实现阶段。

## 9. 故事与功能边界（2026-09-16）

用户提出带游戏情节的产品例子时，先拆成任务、两条路线、失败与返回；明确哪些情节来自用户，哪些补充来自 Agent。“比如”不自动等于最终主题。新前置条件（如访客自带 Key）应同步 PRD 和功能状态，而不只写在视觉故事中。

## 10. 原型交付中的实际检查（2026-09-16）

主题明确选择后直接制作，不反复索要同一授权。功能状态存在不代表画面可见：本次坡后宝箱先被山体挡住，必须通过实际镜头检查修正位置与视角。手机还需检查弹窗滚动和聊天标题换行。对 API Key 一类秘密，原型可用只读假值演示形态，避免预览环节收取真实凭据。

## 11. 交互返工要修正因果关系

2026-09-16 v1.1 实践：用户要求反复铲土和真实爬坡时，不能只把按钮换成新文案。地形和角色要共享高度，动作必须分别改变可观察状态；引用要验证目标段落和返回上下文。导入动画角色需先应用有效姿态，再测量尺寸。检查记录要区分浏览器实际走通、逻辑断言和未检查的真实设备性能。

v1.1.1 实践补充：动作流程要检查“撤回”的出口，例如搬起后应能放下。快捷键复用当前可用按钮与阶段守卫，并过滤输入法、表单和自动重复，避免出现另一套动作逻辑。

## 12. 角色交互不能只验证状态（2026-09-16）

v1.1.2 返工：道具应绑定真正的手部骨骼而非角色根节点；复用动画先观察全身姿态，不能用持枪蹲姿充当搬运。可移动物体的显示位置、交互距离与碰撞必须共用位置来源，不能靠禁止用户移动掩盖脱节。多段旅程用单一时间线控制角色、镜头、提示与目的地，避免多个计时器让场景提前消失。纯逻辑测试之外，必须观察动作发生时的实际画面；审美认可仍由用户决定。

## 13. 核查页面关系要覆盖来源与恢复状态

2026-09-16 v1.1.3：同一详情页可能来自首页、栏目列表或引用，不能把一个固定栏目按钮笼统称为“返回”。检查正向进入、页面返回、浏览器后退/前进、直接链接、取消弹窗以及离页后恢复。除了 URL，还要核对筛选、滚动、输入草稿、提案/结果是否保留。异步结果不能因为用户暂时离开页面就永久停在执行中；呈现层与状态变化应分开。

角色动作检查补充：未被原始动画轨道驱动的关节，增量偏移容易逐帧累积。动作每帧从基准姿态计算，动作结束复位；测试重复采样与动作切换，而不仅检查某一个时间点。场景时间与 UI 完成计时须一致，不能把防止穿模的物理步长上限套到整段演绎时间。

## 14. 镜头意图不等于摄像机路径

“进入角色视线”可以通过剪辑表达，不必把摄像机移动到头部内部。测试需覆盖最终转场而非只检查出舱段；动作应检查实际模型画面，直线插值手部位置可能造成关节奇异姿态。

## 15. 首页不是视觉验收的终点

抽查每一种首页卡片的落点。项目、文章和个人介绍各自需要对应内容的排版系统；不要让首页物件点开后全部退化为同一段落模板。重做布局时保留章节 ID 和导航来源，并在桌面、窄屏检查真实正文。
